# Stitch 18 — a binding is not a boundary

- the assignment was thirty programs. `plans/legacy/stitch-examples-corpus.md`: write thirty new `.st` files for `examples/stitch/`, each with native `test`/`expect` blocks (`test "…" { … }` — [stitch 17](stitch-17-the-tests-were-already-stitch.md) shipped the machinery two weeks before this batch needed it, and the timing was luck, not planning), each one gated by a new host-level check that parses, type-checks, and *runs* every example's own tests before it counts as done. A JSON parser, a toy bytecode VM, a Markov generator, a priority scheduler, a spellchecker, a poker hand ranker, a mustache-style template engine — the kind of corpus you'd want an LM to imitate, per [corpus-mvp.md](../plans/corpus-mvp.md)'s thesis that hand-polished exemplars are the highest-leverage lever on yield.
- the second assignment was implicit and turned out to matter more: keep a running lab notebook — `plans/stitch-examples-findings.md` — of every language limitation, stdlib gap, and outright bug the exercise turned up, on the theory that writing a lot of *real* code in a language teaches you things a design doc and a unit-test suite both miss. It was right. One of the findings was a genuine interpreter defect that had been silently disabling the tail-call trampoline for **any function whose recursive call was preceded by a named binding** — which is most of them — since roughly the moment `let`/pattern-binding support landed. Nobody had noticed because nobody had written enough ordinary recursive Stitch to hit it. This post is what thirty programs found.

## the number, so the rest of this has a scale

- **30 programs, ~6,300 lines, 279 native tests, one real interpreter bug fixed, one documentation section corrected in three places, two natives added, four distinct manifestations of the same parser gotcha, and two stdlib types that turn out not to exist at all.** Every file parses, type-checks, and passes its own tests under a new gate (`stitch/tests/examples.rs`); the full workspace suite and the `no_std` riscv64 build stayed green throughout, because every fix that touched the interpreter got the same TDD discipline the rest of this codebase demands — a failing test first, in its own commit, before the fix.

## a binding is not a boundary — the headline bug

- self-tail-call trampolining was proven in [stitch 11](stitch-11-the-trampoline.md): a direct recursive call in tail position gets caught by `eval_tail_dispatch` and turned into a `TailCall` signal instead of a real Rust stack frame, so `count(n) = match n { 0 => 0  _ => count(n - 1) }` runs a million iterations in bounded stack. That test still passes. It was never wrong. It just never wrote a `let`.
- the toy VM (`vm.st`) needed a self-tail-recursive `step(prog, state) -> Result<Int, Str>` driving a fetch-decode loop, and it faulted with `"call stack too deep"` at `MAX_CALL_DEPTH` (48) after barely fifty instructions — a loop shaped exactly like the proven one, just fetching its next instruction through `match List.at(prog, state.pc) { Some(instr) => match exec(instr, state) { … Ok(Continue(next)) => step(prog, next) } }`. Bisecting with a scratch program pinned the actual variable: it wasn't the nesting, and it wasn't calling a helper function from the match subject. It was that every failing arm **bound a variable** — `Some(instr)`, `Ok(Continue(next))`, or a plain `let` — where the passing stdlib tests all happened to use a wildcard `_` for their recursive arm.
- the root cause, once that was visible, was one line. `Env::bind` — the function backing both `let` and every pattern-match binding — hardcoded `self_closure: None` on the environment it built. `self_closure` is the marker `eval_tail_dispatch` checks to recognize "the function currently applying is the one about to be called again" — the whole mechanism the trampoline runs on. `bind` runs on *every* local binding, not just at a real call boundary, so any `let` or any named (non-wildcard) match arm between the top of a self-tail-recursive function's body and its own recursive call erased the marker before the call ever got a chance to be recognized. A wildcard-only recursive arm was the unusual case; almost every real recursive function destructures its next state by name, or names an intermediate result. This bug was live across nearly the entire space of realistic tail-recursive Stitch, and the existing test suite's `count(n) = match n { 0 => 0  _ => count(n - 1) }`-shaped tests happened to dodge it by construction, not by choosing to.
- the fix is `self_closure: self.self_closure.clone()` in `bind` — preserve, don't reset. Three other `self_closure: None` sites in `env.rs` (`globals_only`, `sibling_module`, `extend_cell`) turned out correct as written: each is a genuine call-boundary-shaped context, either immediately overwritten by `with_self_closure` during real call setup, or an actual scope change. Reading every call site before touching only the one that was wrong is the whole reason this was a one-line fix and not a regression in the other direction.
- verification: a new permanent test, `self_tail_recursive_function_survives_a_let_binding_before_the_call`, same shape as stitch 11's originals but with a `let` and a named match arm ahead of the tail call — RED before the fix, green after. Full `cargo nextest run -p stitch --features testing` (800+ tests), the `no_std` riscv64 lib build (this interpreter ships on the metal), and `cargo clippy` all clean.
- this is exactly [post 69](post-69-the-bug-was-where-no-test-could-reach.md)'s lesson, arriving from the language side instead of the kernel side: the compiler, the review, the test suite — none of them check what you've put out of their reach, so the danger lives exactly there. A trampoline test that only ever recurses on a wildcard has put every realistic recursive function out of its own reach. Writing thirty programs' worth of ordinary Stitch is what put it back in reach.

## the documentation was wrong about the thing next to the bug it caused

- `bank.st` — a small ledger, `mut` accounts, capability-gated audit logging — was designed around `docs/language-design.md`'s claim that a `mut` field "is visible through all aliases (Java/Kotlin semantics, not value copies)." Put an `Account` in a `Ledger`'s `List<Account>`, call `acc.deposit(amount)` on a copy pulled out of that list, and the list is unchanged. The design doc was describing the language SnitchOS was going to have; the interpreter that shipped does something else, on purpose, with its own passing tests proving it (`interp.rs::field_assignment_does_not_alias_a_copy`, `a_mut_method_does_not_alias_a_copy`).
- what actually happens: a `mut` method rebuilds its `@` locally and writes the result back only to the exact place-expression it was called on (`eval_method_call`, and its own comment: *"the result is written back to the caller afterwards (value semantics, so mutation isn't shared until we reassign the caller's place)"*). Two bindings holding "the same" record at some point are not aliases of one heap cell; each is its own copy from the moment they diverged. Calling a `mut` method on a temporary is refused outright — *"cannot call mut method `f` on a temporary — it has no place to write back to"* — which only makes sense under value semantics; a reference-semantics language has no reason to care.
- the practical bite, discovered before it was understood: an object pulled out of a `List` — `find`, indexing, pattern-matching, doesn't matter — is a copy. Mutating it does nothing to the list. Every one of `Ledger`'s methods has to explicitly find, mutate a *local* binding, then fold the result back into `@accounts` (`replaceAccount`, a `map` that swaps the matching element) — the functional-update discipline `List.set` already implies, just made unavoidable instead of a style choice.
- a second, related correction, easy to miss because it's a documentation *omission* rather than a wrong claim: calling a `mut` method on a plain `let` binding is a **runtime error** — `"cannot assign to immutable `x` (declare it with `let mut`)"` — enforced by `env.rs`'s `Scope::assign`, but *not* checked statically yet. `bank.st`'s first draft used plain `let ledger = newLedger()` everywhere and every single test that called a `mut` method on it failed the same way, uniformly, until every one of those bindings became `let mut`.
- fixed `docs/language-design.md` in three places: the type-system intro (dropped "reference-semantic," pointed at the real behavior), the "Mutability is opt-in" bullet (the full correction, citing the proving tests and `bank.st` as the worked example), and the `on`-methods bullet (the runtime-vs-static enforcement nuance). This is the kind of fix `feedback_redundant_data_vs_policy` and the whole "gate the claim, don't trust the prose" thread in these notes exists for — a design doc is a hypothesis about the system, and the system is right there to check it against.

## the natives that didn't exist, closed properly

- `json.st` needed to parse and print integers, and there was no `Str -> Int` conversion of any kind in the stdlib — not `parseInt`, not even `Int -> Str` for printing a number back out. Scoped `json.st`'s numbers to `Int`-only (a documented, deliberate cut, not silent truncation) and hand-wrote both directions: a ten-arm `match` naming every digit character to its value, and the mirror image peeling digits off with `%`/`/`. It works. It's also exactly the kind of thing a native function exists to make unnecessary.
- fixed properly, TDD, same session: `Str.parseInt(s) -> Maybe<Int>` (`text.parse::<i64>()` wrapped in `Some`/`None` — whole-string, no partial parse, no implicit trim) and `toStr(x) -> Str` (exposes the same `Value::display` string interpolation already renders through, so it's free for `Int`/`Float`/`Bool`/`Str` alike). RED tests against the not-yet-existing natives first, then the two implementations. `json.st` was left with its hand-rolled version, as documentation of "here's what you write without the native" — but every later program that needed numeric parsing (`calc.st`, three programs later) used the real thing directly, and it was a non-event.
- one thing the fix *didn't* try to do, on purpose: the batch also found that `Map<K, V>` can't be built from a runtime-computed, variable-length sequence of pairs — only from a literal whose entry count is fixed in the source text. That's a design question (what would a `Map` builder even look like?), not a missing three-line native, and it stayed a documented workaround — an association list, `List<SomeNamedPair>` — for the rest of the batch. `Str.parseInt`/`toStr` were cheap because they're genuinely small; not every gap is.

## maximal munch, four ways

- the project has known since well before this batch that Stitch's grammar has no statement terminator, so a statement beginning with a bare `(` reads as a call of whatever came before it — [stitch 16](stitch-16-the-gap-was-doing-work.md) found this the hard way, sweeping a printer against a million babble-generated programs. This batch found three more shapes of the same underlying fact, each discovered by writing ordinary code, not by fuzzing.
- **statement adjacency**, the original shape: `bank.st`'s `transfer` method had two validation lines, each `(@findAccount(id) |> okOr(…))?`, stacked with no separator. The second line's leading `(` fused with the first line's trailing `?`, producing `"cannot call a a record"` (a mangled error message pointing nowhere near the real mistake). Fixed by prefixing each with `let _ =`, which starts the statement with a keyword instead of a paren.
- **pipe-RHS adjacency**: `tictactoe.st` had `let m = List.at(marks, 0) |> unwrapOr(Empty)` immediately followed by a new statement starting `(m != Empty and …)`. The pipe's right side, `unwrapOr(Empty)`, kept extending its own postfix call-chain across the line into `unwrapOr(Empty)(m != Empty and …)` — a second, nonsense application — and `eval_pipe`'s "is the right side a call" check then evaluated *that* application's callee first, which is `unwrapOr(Empty)` called with one argument. `"function expects 2 argument(s), got 1"` — the right function, the wrong arity, and the actual bug two tokens away. Fixed by dropping parens that weren't precedence-load-bearing in the first place, which happened to remove the leading `(`.
- **match-arm adjacency**, the one that cost the most time to diagnose: `semver.st`'s `comparePre` used `match (a, b) { (Right(_), Right(_)) => 0  (Right(_), Left(_)) => 1  (Left(_), Right(_)) => 0 - 1  … }`. Arm 2's bare-value body, `1`, sits directly against arm 3's tuple pattern, which starts with `(` — same fusion, at a boundary the language's existing gotcha documentation had never named. `1(Left(_), Right(_))` swallows arm 3's own `=>` as a *conditional* arrow, expects `then | else`, and fails with `"expected '|' in conditional"` pointing at arm 3's fat arrow — arm 2's real, unrelated mistake nowhere in sight. Fixed by restructuring rather than patching a single instance: nested single-value matches (`match a { Right(_) => match b { … }  Left(x) => match b { … } }`) instead of one tuple-pattern match, because `Right(_)`/`Left(x)` patterns never start with `(`. `poker.st`, written after this was understood, was designed the nested way from its first draft — five hand-ranking categories, every arm keyed on a `Bool`/`Int` literal, none of them tuples — and it passed the gate on the first try.
- the shape underneath all three: this grammar has no separator between two syntactic units wherever adjacency itself is meaningful — a statement following a statement, a call following a pipe, a pattern following an arm — and every one of those seams is a place a bare `(` silently changes what came before it into something else. Not a bug in any one of the three checks; the same fact about the grammar, recurring wherever the parser has to decide "does this expression keep extending" with no punctuation to ask.

## the escape rule that bit twice, in the file built to avoid it

- json.st already knew, from its own early drafting, that `"{{"` in a Stitch string literal decodes to a single `{` — the interpolation escape (`"temp is {avg}°C"` interpolates; a literal brace is doubled) — not two characters. That finding went in the notebook specifically so the next program wouldn't rediscover it.
- the next program to actually need literal `{`/`}` in a string was `template.st` — a mustache-style `{{var}}`/`{{#each}}` renderer, whose entire purpose is processing `{{`/`}}` syntax. It hit the exact same trap anyway. `Str.split(template, "{{")` and every `"{{#each}}"` in an error message or a test's input template needs the delimiter written **doubled again** — source `"{{{{"` decodes to the value `"{{"` — and the whole file parsed clean with undoubled braces, because to the eye `{{` *is* the delimiter you're picturing regardless of what the lexer does with it. It silently behaved as if every tag were single-braced. Caught by `"Hello, {{name}}!"` rendering as `"Hello, Ada"` with the `!` eaten, and an unrelated `"no match arm matched"` fault on the each-block tests — neither symptom points at the actual cause.
- the honest lesson isn't "remember the rule" — the rule was already written down and remembering it wasn't enough. It's closer to: assume every brace in a string-heavy file is wrong until something external confirms it isn't, the same posture the maximal-munch findings above earn by the second or third recurrence.
- a second, independent bug turned up in the same file, once the brace trap stopped hiding it: `renderEach`'s recursive call had `body` and `items` swapped — `renderEach(List.removeAt(items, 0), body)` instead of `renderEach(body, List.removeAt(items, 0))`. Genuinely my own mistake, not the language's, found by bisecting with throwaway `test "DEBUG …"` blocks — assert an intermediate value against a deliberately wrong constant, read the interpreter's own diff for the real value, narrow, repeat, through `segmentsOf` → `splitEachBlock` → `renderEach` — until the fault's origin was two functions away from where it surfaced. The native test runner turned out to double as a fine `println!`-debugger once you're willing to write assertions you already know will fail.

## the two types that were designed and never built

- `spellcheck.st` wanted `Set<Str>` for a dictionary. `plans/lang/01-grammar-and-precedence.md` documents the design ("`Set<T>` — eager; no literal, `[1,2,3] |> toSet`") in the same breath as `Map`. Grepping `natives.rs`, `value.rs`, and `check.rs` for any trace of `Set`, `toSet`, or a `Value::Set` variant found nothing. Not construction-limited the way `Map` is — never implemented at all, past the design doc. Cost nothing here (a spellchecker's dictionary only ever needs membership testing, and `List` + `contains` gives that for free), but worth knowing before a later program assumes it's there.
- `semver.st` wanted `Either<A, B>` for a version's prerelease field — genuinely two-sided, `Left(tag)` or `Right(())`, where neither side is "the error." `Maybe`/`Result` are registered as literal Rust constructors in `registry.rs::register_builtin_types` (`Some`/`Ok`/`Err`, hardcoded, not something a `.st` file provides); `Either`/`Left`/`Right` are nowhere in that file, or `interp.rs`, or `check.rs`, despite sitting right next to `Maybe`/`Result` in the design doc's list of "just sums." One step short of `Set`'s gap — `sum Either<A, B> = Left(A) | Right(B)` is three words, and once declared it works identically to a builtin, because a `sum` is structurally the same regardless of where it's declared. Still a real "the doc and the ambient globals disagree" trap, and the second time this batch found one.

## the eager/lazy split isn't where it looks like it is

- `markov.st` reached for `drop(words, 1)` to build bigrams — "the list, shifted by one" — and got `"drop expects a Seq, got List"`. `take`/`takeWhile`/`drop`/`dropWhile` are all hard-coded `Seq`-only in `natives.rs`, unlike `fold`/`filter`/`map`, which special-case both kinds explicitly. There's also no `List -> Seq` conversion (`toList` only goes the other way), so there's no bridge — a `List` that needs one of these has to reach for a `List`-native equivalent (`List.removeAt(words, 0)` is "drop 1" for a `List`).
- `diff.st` hit the same family from the other direction: `map(0..=count(b), _ -> 0)` used to seed a DP table row stayed a `Seq` even though the range is finite — ranges are lazy by design, and `map` over a `Seq` returns a `Seq` regardless of whether the source could be materialized cheaply. `List.at` then faulted with `"List.at expects a List, got Seq"`. Fixed with `|> toList`, and worth remembering for any future table-building `map`-over-a-range.
- and `huffman.st` found the one that had been sitting in `json.st` unnoticed the whole time: `Str.split(s, "")`, reached for as "the characters of `s`," is a direct pass-through to Rust's `str::split`, whose documented behavior for an *empty* separator pattern includes an empty-string piece before the first character and after the last (`"abc".split("")` is five pieces, not three; `"".split("")` is two, not zero or one). `frequencies("abracadabra")` came back with a bogus extra `Freq("", 2)` entry; a single-symbol `buildTree("aaaa")` built a two-leaf tree instead of a bare `Leaf`. `json.st`'s `escapeStr` does the identical unfiltered split and is correct anyway, purely by accident of shape — mapping any per-character escape lookup over `""` and rejoining reproduces `""`, so the phantom pieces vanish on their own in a transform-then-rejoin. They only corrupt code that *counts* or *indexes* characters. Fixed with a three-line `chars(s) = Str.split(s, "") |> filter(c -> c != "")` helper, reused in every later file that needed real character-splitting.

## a callback is not a tail call

- `life.st` wanted to drive N generations of Conway's Game of Life, emitting a `life.generation` telemetry span each tick — the obvious shape being a self-recursive loop with `use <- span("life.generation")` inside it. That doesn't trampoline, and confirming *why* mattered more than working around it: `use <-` desugars to the rest of the block becoming a **callback argument** passed to `span`, so the recursive call ends up inside a lambda the native invokes, not in the enclosing function's own AST tail position. `eval_tail_dispatch` only recognizes a direct self-call sitting in tail position; a call reached through a native's callback, however tail-shaped the source reads, doesn't qualify. Verified with a scratch program before committing to a design — `loop(n) uses Telemetry = n <= 0 => 0 | { use <- span("tick")  loop(n - 1) }`, run for a thousand iterations, faulting with `"call stack too deep"` right on schedule.
- not a bug — the direct, correct consequence of how the trampoline is implemented (recognize a literal self-call in tail position, nothing more general) meeting `use <-`'s whole design (the rest of the block genuinely does become a callback). The two are just in tension the instant the callback's body needs to keep recursing.
- the workaround generalized past this one file: don't drive repeated computation with hand-written self-recursion when the point is also a per-iteration effect. Compute the whole sequence first through a *native* loop (`Seq.iterate`/`take`/`toList`, which costs no Stitch-level call-stack depth no matter how long it runs, since it iterates in Rust) and only walk the already-built list with `each` afterward for the effects — `each`/`fold` never touch the trampoline at all, so a callback inside *that* lambda, `use <-` included, never risks the depth counter. `queue.st`, written later, reached for this shape by default rather than rediscovering the fault.

## the checker is stricter than the runtime, and inconsistently so

- `bank.st` established that authority is per-call-boundary at *runtime*: a function gets exactly the `uses` row it declares, independent of its caller — `transferAudited` declares only `FsWrite`, calls `@transfer` (which independently declares and gets `Telemetry`), and it works, matching the refusal-side proof already in `natives.rs`'s own test suite.
- `shell.st` found the static checker disagrees. `runCommand` (a plain function) calling `runLs()` (also a plain function, its own `uses FsRead`) failed the type-check gate — `"performs an effect that needs `uses FsRead`, which is not declared"` — on `runCommand`, which performs no FsRead effect directly. `check.rs::walk_effects` explicitly propagates a called function's declared `uses` up to every caller, for **plain function calls specifically** (`CoreExprKind::Call` with a bare-name callee) — genuinely more conservative than the runtime. But it only pattern-matches that one node shape, never `MethodCall`, so `bank.st`'s identically-shaped `transferAudited`/`@transfer` sailed through clean, because `@transfer(...)` is a method call the effect walker never looks inside. Two asymmetries stacked: static is stricter than runtime, and the strictness only applies to one of two call syntaxes doing the same job.
- `handlers.st` found a third layer the same afternoon. `captureEmits(work)` — a mock-`Telemetry`-handler harness that runs `work()` through a *parameter*, not a known top-level name — never needs `uses Telemetry` itself, exactly as the `shell.st` finding predicts, since `funcs.get("work")` can't resolve a parameter. But every *test* that writes `() -> sumSquares(...)` inline does, because the checker's effect walk is a plain syntactic recursion into `child_exprs`, and a lambda's body is a child like any other — reached whether or not that lambda is ever invoked at the point in the source where it's written. The precise rule isn't "function calls propagate, methods and higher-order calls don't." It's: any *lexically present* named-function call propagates, unconditionally, lambdas-not-yet-invoked included.

## the ceiling that wasn't a missing native

- `elo.st` wanted the real Elo expected-score formula, `1 / (1 + 10^((R_B - R_A)/400))` — a genuine exponential — and there is no `pow`, `exp`, `sqrt`, or any `Float` math of any kind in this interpreter, checked by name across `natives.rs`. Unlike the `Str.parseInt` gap, this one isn't a small missing native; real transcendental math needs either a `libm`-shaped dependency (the project's own `kvetch-model` crate takes exactly that dependency, for the same reason) or a from-scratch series approximation, both out of scope for an example-writing session. Worked around, not routed around: `expectedScorePerMille` is a deliberately-labeled integer piecewise-linear approximation of the logistic curve (a technique some real game engines use to avoid floating point), and a staircase stands in for the textbook `sqrt(margin + 1)` diminishing-returns curve the same way. Filed as the batch's second hard stdlib ceiling, after `Map` construction — worth remembering before any later program assumes real math is available.

## the bugs that were mine, and how they got caught

- `vm.st`'s `Swap` instruction had its two `push` calls nested in the wrong order — reconstructing the original stack order instead of reversing it — caught by hand-simulating the instruction list on paper *before* running it, the same discipline this whole notebook kept recommending to itself. A second bug in the same file, `sumTo`'s loop exit popping the accumulator instead of the spent counter, survived that first check and only showed up once the trampoline fix stopped masking it with a depth fault — caught by an external from-scratch Python reimplementation of the exact same semantics, used as a second, independent opinion rather than re-deriving the same arithmetic by eye a third time.
- the same instinct paid off repeatedly: `markov.st`'s LCG and generation loop, `diff.st`'s LCS table, `tictactoe.st`'s minimax on two crafted endgame positions, `maze.st`'s BFS shortest path, `queue.st`'s tick model (the first draft's produce-then-consume-same-tick ordering made a matched-rate steady state settle at zero instead of a positive backlog — caught by a Python cross-check before any Stitch was written, not after a failing test), `spellcheck.st`'s Levenshtein distances — every one simulated externally first, every one matched the interpreter's actual output once written. A generated candidate that agrees with an independent implementation is worth more than one that agrees with itself.
- and one more real bug of my own, in `template.st`: caught by bisecting with debug assertions rather than by external simulation, because the property under test (a template rendering pipeline) wasn't the kind of thing a five-line reference script could check faster than the interpreter itself could.

## what I learned

- **a binding is not a boundary, and the interpreter had briefly forgotten that.** `Env::bind` treated every `let` and every named pattern match as if it were a fresh call, resetting a marker that should only ever change at a real call boundary. The fix is one line once the distinction is named; finding it needed a program that actually recursed *and* bound something, which a synthetic countdown test never does.
- **a design doc is a hypothesis, and the interpreter is the experiment.** `mut`'s documented semantics and its shipped semantics pointed opposite directions, and the shipped behavior had its own tests proving it deliberate. The doc lost, correctly, because the doc had never been checked against running code.
- **a gotcha that recurs three or four times in different clothes is one fact about the grammar, not three or four bugs.** Statement-adjacency, pipe-RHS-adjacency, match-arm-adjacency — all one fact (no separator, so adjacency is application) wearing different syntax. Once named as one thing, the fourth and fifth instances (`poker.st`) got designed around instead of discovered.
- **knowing a rule and being immune to a rule are different states**, and the gap between them is exactly one distracted moment. The brace-escaping trap was in the notebook before `template.st` was started, and `template.st` hit it anyway, because to the eye `{{` looks like the delimiter it represents regardless of what actually decodes it.
- **get a second opinion from something that isn't your own head**, whether that's an external script, the interpreter's own diff output, or a throwaway test asserting against a value you already know is wrong. Every real bug in this batch that was mine, not the language's, was caught by comparing against an independent source of truth — never by reading the code again more carefully.
- **the corpus effort and the test-runner effort turned out to be the same story from two ends.** [Stitch 17](stitch-17-the-tests-were-already-stitch.md) built `test`/`expect` and asked what a corpus gate should run on; this batch is 279 of the answers, and the gate caught real bugs — in the interpreter, in the documentation, in my own code — on essentially every file that touched anything nontrivial. A corpus that grades itself is worth what it catches, and it caught quite a bit.

## what's next

- `Set<T>` and `Either` are both cheap to close the way `Str.parseInt`/`toStr` were — a native for the first, three words of `sum` declaration turned into an actual stdlib entry for the second — and neither happened this session because neither blocked anything; both are filed. The `Map`-construction gap and the missing `Float` math are real design questions, not omissions, and stay open. The static checker's capability propagation — stricter than the runtime for plain calls, blind to method calls and higher-order calls entirely — is the one finding here that reads like a real inconsistency rather than a documented gap; extending `walk_effects` to method calls, or writing down why that's structurally hard given dynamic dispatch, is the natural next increment whenever the checker gets picked back up.
- the corpus itself is the actual deliverable: thirty gold exemplars, hand-polished, self-testing, sitting exactly where `corpus-mvp.md`'s recipe-matched exemplar selection wants them. What they're worth to an actual model is, as always in this project, the next measurement.
