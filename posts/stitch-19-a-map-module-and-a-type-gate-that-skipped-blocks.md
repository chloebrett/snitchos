# Stitch 19 — a Map module, and a type gate that skipped blocks

- [stitch 18](stitch-18-thirty-example-programs.md) closed with a list of things thirty example programs had found and *not* fixed. Two were dismissed as cheap-but-unblocking, two as real design questions. The biggest of the design questions was this: **`Map<K, V>` cannot be built from runtime data** — only written down as a literal whose entry count is fixed in the source text. Twelve of the thirty programs had worked around it by declaring an ad-hoc key/value `prod` and hand-writing the linear scan `Map` would otherwise give for free. That post's own words: *"a design question (what would a `Map` builder even look like?), not a missing three-line native."*
- it had an answer, and the answer was smaller than the question. This post is that work — eleven TDD increments, a `Map` module, and the twelve workaround files converted back. But the thing worth writing down isn't the module. It's that this session kept running into **checks that pass without checking**: an equality operator that cannot see the contract it appears to be testing, a mutation-testing tool that reports green because it had nothing to say, a guard that has never once failed. Three different shapes of the same hazard, in one session, and each one caught something real once it was made to bite.

## the number, so the rest of this has a scale

- **11 increments, 10 natives, 3 existing combinators taught a fourth collection kind, 32 new tests, 18 hand-written mutants, 13 `prod` declarations deleted across 12 corpus files, one silent-overwrite bug in the native registry, one false claim removed from the design doc.** The `stitch` suite finished at 789 green (it was 753 when this started, the rest of that delta being work from other sessions); `cargo xtask itest` and `--scramble` stayed at 100% fidelity throughout; the `no_std` riscv64 lib build was checked every increment, because this interpreter ships on the metal and a native that reaches for `std` breaks the board rather than the host suite. Plan, decisions and rejected alternatives: [../plans/legacy/stitch-map-you-can-build.md](../plans/legacy/stitch-map-you-can-build.md).

## the API got smaller as the capability got bigger

- the plan opened with a ten-operation surface, `Map.size` included, and the first two increments deleted four of them before they were written. The move was to stop treating `Map` as a new thing needing its own vocabulary and teach the *existing* vocabulary about it: `fold`, `map` and `filter` accept a `Map`, iterating `(key, value)` tuples. That's one match arm each.
- because the entire prelude is fold-derived — `count`, `any`, `all`, `contains`, `find`, `first`, `last`, `min`, `max`, `flatten` are all folds over `fold` — teaching `fold` about `Map` lit every one of them up for free, in a single increment, with no `Map.`-prefixed duplicates. `count(m)` is `Map.size`, so `Map.size` was struck from the plan. So were `Map.any`, `Map.find` and `Map.each`, which I would otherwise have added one at a time without noticing they were already there.
- `map` over a `Map` returns a **`List`**; `filter` returns a **`Map`**. Projecting an entry to an arbitrary value loses the key shape; a predicate selects entries without transforming them. Kotlin makes the same split for the same reason, and it reads correctly at a glance once you've seen it twice.
- the survivors got audited by the same test. `Map.entries(m)` is exactly `map(m, e -> e)` and is kept anyway — it's the named inverse of `Map.fromList`, and the round-trip law reads as a law only with both names present — but that redundancy is now asserted *in the suite*, so anyone who wants to cut it can see precisely what the replacement spelling is. `Map.keys`/`Map.values` are not similarly derivable; their `map`-based spellings need a `match` wrapper to reach past the tuple, and read horribly.
- `Map.has` looked like the most obviously redundant member of all, next to a prelude that already has `contains`. It isn't, and the test that proves it is the nicest small thing in this batch: now that `fold` accepts a `Map`, `contains(m, v)` folds over *entries*, so it asks "is `("a", 1)` an entry?". Ask it about a bare key and it doesn't quietly answer `false` — `==` is strict across kinds, so it **faults**: `"operator Eq cannot apply to Tuple and Str"`. `contains` cannot stand in for key membership even by accident.

## unordered equality, or: the assertion that cannot see the thing it's asserting

- insertion order is a **contract** for this `Map`, not an implementation detail. It's what makes a map you *build* interchangeable with one you *write down*: the literal already keeps a duplicate key in its first position while taking the last value (`interp.rs`'s `CoreExprKind::Map` arm), so `Map.insert` has to agree or the two spellings diverge.
- and `Value`'s equality for maps is **unordered** — same size, every entry matches, order irrelevant. Which means `Map.insert(m, "a", 99) == ["a": 99, "b": 2]` is completely blind to a reordering. The obvious assertion cannot see the contract.
- this cost me coverage three separate times before it became reflex. The first was `filter` in increment 2, where the fix came from reading `value.rs` before writing the test rather than after. The second was increment 5's headline mutant: replace `insert`'s find-and-update-in-place with a retain-then-push that re-appends the key at the end, and **three of that increment's four tests still pass** — equality passes, `count` passes, the built-vs-literal test passes, because building `[:] → "a" → "b"` never replaces an existing key at all. Only the key-order assertion fails.
- the third was in the corpus, and it was the one that would have shipped. `logstats.st` and `inventory.st` both have a test named "…first-seen order", and the `List<LevelCount>` version asserted that order **for free**, as a side effect of list equality. Translating the assertion to a bare `Map` comparison keeps the test green while testing strictly less than it did before. Every converted file now carries an explicit `Map.keys(m) == [...]` beside its equality check, with the reason written next to it.
- the general shape: when you change a representation, a test that still passes has told you nothing about whether it still *tests*. The equality operator changed meaning underneath the assertion and stayed green about it.

## the mutation tool had nothing to say, and said it in green

- this codebase treats mutation testing as a real gate — `cargo xtask mutants`, a documented equivalent mutant, the whole discipline. So every increment ran it. Increment 1: 103 mutants across `natives.rs`, 2 missed, 6 timeouts, all pre-existing. Looks fine.
- except the only mutant cargo-mutants generated *inside the new code* was a whole-function replacement, and it was **unviable** — it doesn't compile, because `Value` has no `Default`. Scoping the run to just the changed functions in increment 2 made it unmistakable: three mutants, three unviable, and a literal `WARN No mutants were viable`.
- the reason is structural, not a configuration problem. A collection native's body is destructure, loop, construct, return. There is no binary operator, no comparison, no boolean — nothing for a generic mutation operator to perturb. Every increment of this plan had that shape, so the tool was blind to all of it, and would have reported green for all of it.
- there is a tempting fix that makes it worse. `mutants.toml` can supply an `error_value` so `Err(RuntimeError::new(…))` compiles, which turns those unviable mutants into viable ones. They'd all be whole-function replacements that any test kills instantly. The report goes green, the coverage doesn't move, and the gate now actively lies. An honest gap beats a dishonest tick.
- so the MUTATE step became hand-mutation: eighteen of them across nine increments, each one a specific claim the tests make. Reverse the entry order. Swap key and value in the tuple. Return a `List` where a `Map` is owed. Have `expect_map` swallow its refusal. Apply `f` to the default when the key is absent. Every one died, and two of them justified test assertions I'd otherwise have called defensive.
- worth being precise about what this does and doesn't say. `cargo-mutants` isn't broken and this isn't a feature request; the mutants that matter for data-shape code are *semantic* — order, position, container kind — and no generic generator produces those. It's also not what [../docs/stitch-mutation-testing-design.md](../docs/stitch-mutation-testing-design.md)'s planned Stitch-level tool would fix either: that one mutates `.st` programs, not the Rust running them. Two mutation tools, neither covering this gap. Hand-mutation stays in the loop for this kind of code, and that got written down in the design doc rather than left as folklore.
- the same doc got two other corrections while I was in there, both of them prerequisites that had quietly shipped since it was written: `test "…" { expect … }` is the test convention it proposed inventing, and `DEFAULT_FUEL` + `Verdict::Exhausted` are the fuel cap and the timed-out bucket it asks for. Its first milestone is now smaller than written, and its first target should be the thirty-program corpus rather than stim's FSM — thirty programs with 280+ assertions already loaded and run by an existing harness, which didn't exist when the page was captured.

## the third green check: a guard that had never failed

- the last native was `Map.mapValues`, and I flagged the name as a cosmetic worry — it sits awkwardly beside `Map.values`. It wasn't cosmetic.
- every native is registered flat under its internal `name` (`interp.rs`'s `register`), and `builtin_modules` then looks each module member up by that same name. `mapValues` was **already taken** as the internal name for `Map.values`. A second one doesn't collide loudly: it silently overwrites the first in a `BTreeMap`, and *both* module members then resolve to whichever won.
- nothing detected that. So before writing the native I added two guards — every native has a unique internal name, every builtin module member has a unique export name — and they passed on arrival, which is exactly the state a guard is least trustworthy in.
- so I made it fail on purpose: registered the new native under the naive colliding name and ran. The guard fired, *and* `Map.values(["a": 1, "b": 2])` faulted with `"mapValues expects 2 argument(s), got 1"` — it had resolved to the new native. Both halves confirmed: the hazard is real, and the guard can see it. Then the internal name became `mapMapValues`, per the `<module><Member>` convention the `Str`/`List` modules already use, and everything went green for the right reason.
- this is `feedback_control_that_cannot_discriminate` arriving in a new costume. A guard that has never failed is indistinguishable from a guard that cannot fail, and the cost of telling them apart was one deliberate wrong commit and sixty seconds.

## the doc claimed a compile error that does not exist

- `docs/language-design.md` on map keys: the mutable-hash-key footgun is designed out by separating equality from key-eligibility, so *"using a value with any `mut` field as a `Map`/`Set` key is a **compile error**."*
- there is no `Key` contract, no `Hashable` contract, and no check anywhere in `stitch/src/` that rejects a `mut`-field key. The rule is designed, not built.
- what actually happens is milder than the footgun the rule was written against, and worth knowing: because `Value::Map` is an association vector compared structurally, a mutated key doesn't corrupt a hash bucket — it just stops comparing equal to the key you inserted, and lookups silently miss. Still a trap, different trap.
- that's the **fourth** doc-vs-implementation divergence this corpus effort has found, after `mut`'s semantics, `Either`, and `Set` — all four found by someone trusting the page. So `Set` got an explicit *"`Set<T>` does not exist"* bullet rather than remaining an absence for the next person to discover, and the `Map` contract (insertion-ordered, persistent, in the combinator vocabulary, O(n) today) got written down properly for the first time.

## the fork worth arguing about

- `Map.update(m, k, default, f)` is the operation six of the twelve workaround files were actually reaching for, and it has two defensible readings that differ *only* on an absent key: insert `default` raw, or insert `f(default)`.
- I specified the second, for the sake of one algebraic law — `update(m,k,d,f) ≡ insert(m, k, f(unwrapOr(get(m,k), d)))` — which makes the tally read `Map.update(acc, w, 0, $ + 1)`, "counter starts at zero". I also filed the alternative as "Elixir's", implying an outlier.
- that framing was wrong twice. It's the majority convention — Rust's `entry(k).or_insert(d)`, Haskell's `insertWith`, Kotlin's `merge`, Elixir's `Map.update/4`; Clojure's `fnil` is the outlier and is an explicit wrapper. And more decisively, **the raw-default form is strictly more expressive**: mine is the special case you get by passing `f(d)` as its default, while the reverse fails whenever the first-seen value lies outside `f`'s image. Want first-seen 5 with `f = $ * 2`? There is no `Int` that doubles to 5.
- so the specified semantics lost to the containment argument, the tally reads `Map.update(acc, w, 1, $ + 1)`, and the case my version couldn't express is now pinned by a test — `Map.update([:], "k", 5, $ * 2)` giving 5 — so the choice lives in the suite rather than only in an archived plan. The lesson is that a name carries semantics: shipping the other reading under the signature four languages already use would have been a silent off-by-one for anyone with those priors.

## the corpus paid it back

- twelve files converted, thirteen `prod` declarations deleted, every file's own tests as the regression net. Two of them — `logstats.st` and `inventory.st` — contained the *same five-line O(n²) `fold`/`find`/`map` tally, written independently in unrelated files*. Both are now one expression.
- `lru.st` disproved its own header comment, which said a `Map` "couldn't give the recency order for free even if it existed". Wrong twice over: `Map` preserves insertion order, and re-inserting a key after removing it appends it — so remove-then-insert *is* the recency bump, entry order *is* recency order, and eviction takes the first key. Every recency test passed unmodified.
- `trie.st` was the file where the workaround cost the design rather than just verbosity, and converting it collapsed two branches into one. The `List` version needed separate append-vs-replace cases because those are different list operations; keyed insert doesn't distinguish, so `Map.get(children, c) |> unwrapOr(empty())` handles both. But the comment says plainly that this is a **clarity win, not yet a speed one** — `Map` is still an association vector, so a 26-way branch is still a 26-element scan. What changed is that the code now says "keyed lookup" instead of open-coding one, so the day the representation becomes a hash, this file gets faster without being touched.
- `formula.st` needed an assertion *replaced* rather than translated. Its diamond-dependency test asserted the shared ancestor appears exactly once in the memo cache — which caught a skipped cache-hit check by finding a duplicate. A `Map` cannot hold a duplicate, so that assertion becomes true by construction and stops testing anything. What it was really checking is that the cache is *consulted*, so it now seeds the cache with a wrong answer and requires the result to be built from it.
- `poker.st`'s `RankCount` survived on its merits, and saying so matters as much as the deletions: only its tally construction converted. `classifyByCount` reads `top.rank`/`top.count`/`second.rank`/`second.count` a dozen times, where tuple entries would need a `match` at every use. That's [stitch 18](stitch-18-thirty-example-programs.md)'s named-`prod`-over-tuple rule earning its keep, not a workaround to sweep up. "Convert everything" would have made that file worse.
- `json.st` took one deliberate behaviour change: a duplicate key now resolves last-wins, `Map`'s rule and JavaScript's, instead of keeping both copies. Documented in its header rather than discovered later.

## two small things the language did that I didn't expect

- **a placeholder binds to the innermost enclosing call.** `Map.mapValues(["a": 1], toStr($))` faults with `"cannot call a Str"`, because `toStr($)` is `toStr(y -> y)` — `toStr` applied to the identity lambda — not `x -> toStr(x)`. The design doc's rule ("anything nested → write the explicit lambda") is load-bearing rather than stylistic, and the failure mode names a completely unrelated symptom.
- **`flatMap` still doesn't accept a `Map`.** Only `fold`/`map`/`filter` were taught, so `trie.st`'s `wordsUnder` goes through `Map.entries` first, with a comment saying why. That's a fresh data point for the standing finding that the eager/lazy/keyed split in this stdlib isn't uniform — the same complaint `markov.st` filed against `Seq`-only `drop` two posts ago, one collection kind later.

## what I learned

- **a green check and a check are different things, and the gap is invisible from the outside.** Unordered equality passing, a mutation report with no viable mutants in it, a guard that has never failed — all three look exactly like success. Each one needed a deliberate act to tell apart: read the equality implementation, scope the mutation run, commit the wrong name on purpose. None of that is expensive; all of it has to be chosen.
- **the coverage question isn't "does this test still pass" but "does this test still test".** Three assertions in this session kept passing while quietly ceasing to check anything — first-seen order under `Map` equality, "appears exactly once" under a type that can't duplicate, an insert contract under a built-from-empty example. A representation change silently rewrites what your assertions mean.
- **capability can go up while surface goes down.** Teaching three existing combinators about one new kind deleted four planned natives and lit up ten prelude functions. The instinct to give a new type its own vocabulary is the expensive one; the cheap move is to make it fit the vocabulary already there.
- **a name carries semantics whether you meant it to or not** — both in the large (`update` means the raw-default reading in four languages, and shipping the other one under that signature is a trap) and in the small (`mapValues` was already taken, and the registry silently let me take it twice).
- **converting everything is not the goal.** `poker.st` kept its named pair, `json.st`'s scan still accumulates a `List` before one `Map.fromList` at the close brace, and `graph.st`'s `addEdge` deliberately isn't `Map.update` because `update` would *create* an entry for an unknown node and the no-op is documented behaviour. A migration that doesn't ask "does this one earn it?" is just a find-and-replace with extra steps.

## what's next

- the `Map` representation is still an association vector, so every one of these programs got clearer without getting faster. Swapping in a hash or a tree is interior work the bytecode-VM stage owns, and it's now bound by a published ordering contract — which is the right constraint to have written down *before* the swap rather than discovered during it.
- the `Key`/`Hashable` rule is designed, documented as unbuilt, and unscheduled; it needs checker work. `Set<T>` stays cut. `flatMap`-over-`Map` and the wider eager/lazy/keyed non-uniformity are one increment whenever the stdlib gets picked up again.
- eleven proposals from [../plans/stitch-language-improvements.md](../plans/stitch-language-improvements.md) remain, and the two at the top are the interesting ones: newline-aware postfix parsing, which would kill all four shapes of the maximal-munch gotcha [stitch 18](stitch-18-thirty-example-programs.md) catalogued; and `expect fault`, without which the language's headline feature — capability refusal — cannot be tested in the language itself. That second one is also the prerequisite for closing the checker's effect-propagation holes, because you cannot test-drive a refusal rule you have no way to assert.
